## أرشيف نسخة Python السابقة


نسخة تطوير أولية أنشئت من الأكواد الواردة في المحادثة ورفعت إلى المستودع الجديد `margalali-bit/CAFE-SELECTION-` على فرع `develop`. المستودع الجديد كان فارغاً؛ لم يتم نقل ملفات من المستودع السابق المتعذر الوصول إليه.

## التشغيل على Windows

يتطلب Python 3.12:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m desktop_pos.main
```

عند أول تشغيل، أنشئ حساب المالك باسم وPIN من 6 إلى 12 رقماً. لا توجد رموز افتراضية. بعدها أضف المنتجات والنادل من لوحة المالك. البيانات في `%LOCALAPPDATA%\CafeSelection\cafe.db`. اضبط توقيت Windows على المغرب. احفظ مجلد البيانات والنسخ الاحتياطية بصلاحيات نظام تشغيل مقيدة؛ قاعدة البيانات غير مشفرة.

المتاح: الدخول الآمن نسبياً برمز PIN مجزأ ومملح، قفل مؤقت بعد خمس محاولات خاطئة، صلاحيات في طبقة العمليات، منتجات، سلة، تسجيل طلب مدفوع محلياً، مصاريف، تقارير يومية وشهرية، Excel، إضافة نادل وتغيير PIN، نسخ احتياطي يدوي باستخدام SQLite Backup API مع فحص السلامة. تغيير PIN ينهي جلسات الحساب.

الصافي المعروض = المداخيل المسجلة ناقص المصاريف المسجلة؛ ليس ربحاً محاسبياً نهائياً دون تكلفة المخزون والضرائب وغيرها. لا توجد قائمة منتجات مفترضة أو شعار مرفق.

## الاختبارات

```powershell
python -m unittest discover -s tests -v
```

Windows Actions مهيأ لبناء ملف واحد `CafeSelection.exe` باستخدام PyInstaller، وليس مثبتاً موقعاً. يبدأ بناؤه عند رفع التغييرات إلى فرع التطوير. يُشغّل تلقائياً عند الدفع إلى `develop`، وتوجد إمكانية تشغيل يدوي إذا كان ملف workflow موجوداً في الفرع الافتراضي. بعد نجاح البناء: Actions ← Windows POS ← Artifacts ← CafeSelection-Windows؛ فك ZIP ثم شغّل الملف التنفيذي.

## خطة التطوير

1. **الأساس المحلي (هذا التسليم):** البيانات، الصلاحيات، الكاشير، المصاريف، الملخصات والاختبارات.
2. **إكمال سطح المكتب:** تعديل الكميات، التصنيفات، تعطيل الحسابات، سجل التدقيق وإلغاء الطلبات بصلاحية المالك، تقارير المنتجات والنادل، PDF عربي بخط مرفق، نسخ احتياطي تلقائي، الطباعة وإعادة الطباعة دون تسجيل بيع جديد.
3. **Supabase:** مخطط متعدد الأجهزة، مصادقة المالك والجهاز، RLS واختبارها، RPC لحفظ الطلب وتفاصيله ذرياً بمعرف UUID ثابت. إرسال outbox ثم تأكيده محلياً فقط بعد إقرار الخادم؛ إعادة المحاولة بعد الانقطاع دون تكرار. لا تُرفع PIN أو تجزئتها. مفاتيح service_role تبقى على الخادم فقط.
4. **Flutter Android:** دخول المالك، المداخيل والمصاريف والطلبات، توفر المنتجات مع إصدارات لمنع الكتابة فوق تعديلات أحدث. إعادة الاتصال والتحديث الآمن لخيط Qt في الكاشير. إعداد Android Actions بعد وجود مشروع قابل للبناء.
5. **الإشعارات والتحقق الميداني:** FCM من الخادم بعد تسجيل طلب جديد، ثم اختبار انقطاع الشبكة، استعادة النسخ، ضغط العمل والطابعة الفعلية.

السحابة والهاتف والطباعة وPDF والإشعارات لم تُنفذ بعد. جدول outbox يحفظ أحداث الطلبات والمصاريف لكنه لا يرسلها حالياً. لا تُعد البيانات متزامنة قبل تنفيذ المرحلة الثالثة. عند انقطاع الإنترنت تصل تغييرات المنتجات والإشعارات بعد استعادة الاتصال، وليس فوراً.

لا تضع أسراراً في Git أو الهاتف أو تطبيق الكاشير. يلزم إتاحة المستودع الأصلي لمراجعة الملفات ودمج هذا العمل في فرع تطوير منه؛ لا ترفع هذه النسخة فوقه مباشرة. كل دمج في main يسبقه عرض التغييرات والاختبارات للمراجعة.
