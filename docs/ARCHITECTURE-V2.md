# تنفيذ بنية Café Sélection — 16 نوفمبر 2026

المصدر: الملف المرفق `cafe-selection-architecture.pdf`. اعتُمد كمتطلبات منتج، ولم تُعتبر عباراته عن «كود مكتوب» دليلاً على ملفات موجودة. الفرع: `feature/architecture-v2`. لا دمج في main. المشروع القديم Python محفوظ.

## القرار والتنفيذ

- `electron_pos/`: تطبيق Electron بواجهات HTML/CSS/JS عربية للمس. SQLite WAL داخل عملية Electron الرئيسية، مع preload محدود وcontextIsolation وsandbox وCSP. لا يصل renderer إلى الملفات أو SQL.
- `src/main/service.cjs`: تحقق الأسعار والصلاحيات وحالات الوردية والديون، داخل معاملات SQLite. المالك يدير ولا يسجل المبيعات؛ النادل يسجل ويقبض نقداً. حساب المالك يُنشأ عند أول تشغيل دون PIN افتراضي. PIN مع scrypt وملح، وقفل دقيقة بعد خمس محاولات، وجلسات بحد أقصى ثماني ساعات من الخمول.
- اليوم التجاري باستخدام `Africa/Casablanca` وبداية 05:00 قابلة للتعديل عند إغلاق الورديات. UUID عالمي بالإضافة إلى رقم يومي متسلسل. إعادة الطلب بنفس request_id ترجع الطلب نفسه. سعر الطلب محفوظ، ولا يتغير بتعديل القائمة.
- إلغاء النادل لطلباته في وردية مفتوحة مع سبب. إلغاء المالك بعد الإغلاق يعيد حساب المفروض والفرق ويعيد الوردية إلى انتظار التأكيد. لا حذف للطلبات. منع إلغاء دين سُدد جزئياً حتى لا يُنشأ رصيد سالب دون عملية استرداد معتمدة.
- الطلب على الحساب يزيد الدين ولا يزيد الإيراد. التسديد يُسجل في يومه التجاري. حصيلة الوردية = الطلبات النقدية غير الملغاة فقط؛ التسديدات في سجل مالي مستقل، ولا تدخل هذه الحصيلة تلقائياً.
- التذكرة 80mm: رقم يومي ووقت ونادل وأصناف ومجموع وشكر، دون PIN أو طاولة أو TVA. عرض وإعادة طباعة وPDF من الطلب المسجل. نافذة طباعة Windows باختيار الطابعة؛ لم يُختبر جهاز حراري فعلي ولم تُضف قناة USB ESC/POS خام.
- Excel وPDF للتقارير، PDF للتذاكر، وتقارير يومية/شهرية وتفاصيل المنتجات. التقرير الشهري يعرض أيام الحركة. قاعدة البيانات غير مشفرة؛ تعتمد حماية الملف على صلاحيات حساب Windows والقرص.
- نسخة محلية عند التشغيل وكل 24 ساعة عبر SQLite backup API، ونسخة يدوية مفحوصة. لا حذف تلقائي لنسخ قديمة في هذه النسخة.

## المزامنة

كل تعديل مالي أو إداري يضيف حدثاً صغيراً في outbox في المعاملة نفسها، دون نسخ التاريخ المالي كاملاً لكل بيع. الإرسال مرتب بدفعات حتى 100 حدث مع لقطة قراءة واحدة حديثة بلا PIN ولا تجزئته، وإقرار الدفعة يأتي بعد معاملة Supabase. تُرسل حالة اليوم عند تشغيل الجهاز وعند تغير اليوم التجاري حتى لو لم تُسجل مبيعات جديدة. الخادم يمنع تكرار event_id وdevice_id/seq ويمنع لقطة أقدم من الكتابة فوق أحدث. الاختبار يحاكي وصول الحدث وضياع إقراره ثم إعادة الإرسال.

هذا تصميم أولي لمقهى وجهاز كاشير واحد، مع لقطة JSON مركزية للقراءة بدلاً من إعادة بناء كل جداول التشغيل في السحابة. واضح وبسيط للربط الأول، لكنه ليس مناسباً لتراكم سنوات من الطلبات دون تقسيم إلى دفعات/جداول سحابية وأرشفة. لا يُدعى دعم أجهزة كاشير متعددة.

تطبيق المالك ينشئ أوامر، ولا يغيّر رصيد SQLite مباشرةً. الجهاز يتحقق من الأمر ويطبقه ويؤكد نتيجته. أوامر مدعومة: السعر والتوفر، إعدادات الديون، إلغاء طلب، تأكيد وردية، تسجيل تسديد. التحقق من إصدار المنتج يمنع الكتابة على تعديل أحدث. فشل التحقق يظهر كأمر مرفوض. معرّف الأمر محفوظ محلياً لمنع إعادة تطبيقه بعد انقطاع الإقرار. كما يحفظ الهاتف UUID للأمر في SecureStore قبل الإرسال، ويعيد استخدامه إذا ضاعت الاستجابة أو أُعيد تشغيل التطبيق.

**أثناء انقطاع الإنترنت لا يمكن منع الطلب من الهاتف لحظياً.** إعدادات الديون المحلية المعتمدة تبقى فعالة حتى وصول أمر التغيير. الطلبات الصحيحة التي سُجلت دون شبكة تبقى محفوظة وتزامن لاحقاً؛ لا تُرفض بأثر رجعي بسبب أمر هاتف لم يصل بعد. هذا يحفظ المصدر المحلي للبيانات. سياسة مالية أشد تتطلب حظر البيع دون اتصال وتخالف استمرار العمل المطلوب.

لا تستعد نسخة محلية قديمة فوق قاعدة إنتاج متزامنة دون مصالحة seq والسحابة وتوثيق الاستعادة؛ لا توجد أداة استعادة تلقائية في هذه النسخة.

## Android

`mobile_owner/` تطبيق Expo / React Native: دخول المالك بالبريد وكلمة المرور، ثم TOTP، تخزين الجلسة عبر SecureStore، لوحة اليوم، الطلبات، الأسعار والتوفر، الورديات، أرصدة الديون وحالة الأوامر. القراءة المباشرة محمية بسياسة MFA aal2. تظهر حالة وآخر وقت مزامنة بدلاً من الادعاء بأن بيانات قديمة مباشرة.

إضافة النادل وPIN من الكاشير فقط؛ الهاتف يعرض أرصدة الديون ويمكنه إرسال أمر تسديد، ويُؤرخ التسديد بيوم تطبيق الأمر على الكاشير. إشعارات Expo تحتاج EAS وFCM وعامل الخادم المجدول. عامل الإشعارات يرسل تنبيهاً عاماً دون بيانات مالية حساسة إلى رموز أجهزة المالك. الشبكة قد تسبب إعادة إرسال إشعار؛ منع تكرار الطلبات المالية مستقل عن تسليم الإشعارات.

## الاختبارات وحدود التحقق

- اختبارات Node للنقد والصلاحيات وPIN والورديات والديون والإلغاء والنسخ.
- تنفيذ SQL في PostgreSQL مضمّن PGlite مع محاكاة auth؛ يتأكد من RLS وعزل حساب الجهاز وحساب آخر، واشتراط aal2، ومنع تعديل حالة السحابة مباشرة، ومنع تكرار الحدث. هذا لا يعوض تجربة مشروع Supabase حقيقي.
- Chromium مع قاعدة SQLite معزولة: إعداد المالك، القائمة، النادل، تفعيل الدين والزبون والمصاريف، بيع نقدي وبيع على الحساب وتذكرة، إغلاق وتأكيد وردية، تقرير شهري، وعرض 1024px. صور فعلية في `docs/`.
- تشغيل Electron الأصلي على عامل Windows وتوليد PDF تذكرة 80mm نجحا. محاولة تشغيل Electron دون شاشة Linux اصطدمت بغياب display؛ استُخدم عامل Windows للتحقق الأصلي.
- TypeScript وتجميع حزمة Android عبر Metro. لا هاتف أو محاكي Android متاح للفحص هنا.
- GitHub Actions منفصل لـ Windows Electron ولـ APK تطوير مستقل عن Metro. APK موقّع بمفتاح التطوير الافتراضي؛ يلزم مفتاح إصدار خاص قبل نشر Google Play.

## ما يتطلب إعداداً خارج الكود

مشروع Supabase وحسابات المالك والجهاز، بيانات EAS/FCM، شعار المقهى الأصلي وقائمة المنتجات الفعلية، وتجربة طابعة 80mm. لا مفاتيح حقيقية مرفقة، ولم يُنشأ مشروع سحابي أو تُنشر وظيفة خارجية تلقائياً.
